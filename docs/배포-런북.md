## 1. 전체 흐름

```text
[팀원] feature 브랜치 → push → PR(base: develop)
        └→ GitHub Actions CI (자동 검사)
        └→ 이상 없음 → merge → develop 반영
                                        │
[우리] develop → PR(base: main) → 리뷰 → merge
        └→ Cloud Build (자동) → 빌드 → 이미지 push → Cloud Run 배포 🚀
        └→ 3~5분 후 반영
```

| 단계         | 도구                            | 소요  |
| ------------ | ------------------------------- | ----- |
| CI 자동 검사 | GitHub Actions `ci.yml`         | 2~4분 |
| 자동 배포    | Cloud Build (`cloudbuild.yaml`) | 3~5분 |

| 주소          | 값                                           |
| ------------- | -------------------------------------------- |
| 프론트 (prod) | `https://docthru-alysvay2yq-du.a.run.app`    |
| 백엔드 (prod) | `https://docthru-be-xwfe2o3yfa-du.a.run.app` |

## 2. 브랜치 규칙

| 브랜치         | 하는 일       | PR base     | 보호 규칙                    |
| -------------- | ------------- | ----------- | ---------------------------- |
| feature (개인) | 자기 작업     | → `develop` | 없음                         |
| **develop**    | 검증된 통합본 | ← feature   | PR 필수 + CI 필수            |
| **main**       | 발표용 확정본 | ← develop   | PR 필수 + CI 필수 + 리뷰 1개 |

**처음 작업하기 전에 (한 번만)**

```bash
git checkout develop
git pull origin main     # main 의 뼈대·인프라를 develop 으로 당겨옵니다
```

> `develop` 은 `main` 보다 뒤처져 있을 수 있어요. 위 한 줄로 당기고 시작하면 됩니다.

**자기 브랜치 만들기**

```bash
git checkout -b feat/<내기능>
```

## 3. CI 는 언제 돌까

`.github/workflows/ci.yml` 의 트리거:

| 이벤트          | 대상                           | 검사 |
| --------------- | ------------------------------ | ---- |
| `pull_request`  | develop PR · main PR **둘 다** | ✅   |
| `push`          | `main` · `develop`             | ✅   |
| `workflow_call` | deploy.yml 이 재사용           | ✅   |

**CI 가 하는 일 (순서대로)**

| 스텝         | 내용                                                    |
| ------------ | ------------------------------------------------------- |
| Install      | `pnpm install --frozen-lockfile` (lockfile 그대로 재현) |
| Test         | `pnpm test`                                             |
| Lint         | `pnpm lint`                                             |
| Format check | `pnpm format:check` (포맷 틀리면 실패)                  |
| Build        | `pnpm build`                                            |
| Build image  | `docker build` — **이미지가 올라가는지**까지 확인       |

> FE 는 DB 가 필요 없어서 postgres 서비스를 띄우지 않습니다. 비밀값도 하나 필요 없어요.

## 4. 자동 배포 (Cloud Build)

| 항목             | 값                                                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| 트리거           | `Build-and-deploy-to-Cloud-Run-service-docthru-on-push-to-main`                                                       |
| 감시 브랜치      | `^main$` (develop 은 **배포하지 않습니다**)                                                                           |
| 설정 파일        | [`cloudbuild.yaml`](./cloudbuild.yaml) (repo 안에서 버전 관리)                                                        |
| 이미지           | `asia-northeast3-docker.pkg.dev/th-docthru-team2-fe/cloud-run-source-deploy/15th-docthru-team2-fe/docthru:<커밋해시>` |
| Cloud Run 서비스 | `docthru` (리전 `asia-northeast3`)                                                                                    |
| 인스턴스 상한    | 3 (무료 티어 과금 방지)                                                                                               |

**주소를 바꾸고 싶다면** → `cloudbuild.yaml` 의 `substitutions` 한 곳만 고치고 main 에 머지하면 됩니다.

> ⚠️ **GitHub Actions 의 `deploy.yml` 은 예비(수동) 경로**입니다.
> 공식 자동 배포는 Cloud Build 가 담당해요. `deploy.yml` 은 Cloud Build 가 막혔을 때나 지금 당장 수동 배포가 필요할 때 씁니다.

## 5. 빌드 인자가 왜 필요한가

`next.config.mjs` 의 `rewrites` 주소와 `layout.js` 의 `metadataBase` 는 **빌드 시점에 이미지 안에 박힙니다.**

| 값                     | 읽는 곳                          | 시점        | 기본값                         |
| ---------------------- | -------------------------------- | ----------- | ------------------------------ |
| `NEXT_PUBLIC_SITE_URL` | `layout.js` `metadataBase`       | **빌드 시** | `http://localhost:3000`        |
| `BACKEND_BASE_URL`     | `next.config.mjs` `rewrites`     | **빌드 시** | `http://localhost:5010/api/v1` |
| `BACKEND_BASE_URL`     | `src/lib/api.js` (서버 컴포넌트) | 실행 시     | `http://localhost:5010/api/v1` |

> **실행 시 환경변수를 줘도 rewrite 주소는 안 바뀝니다.** 그래서 `Dockerfile` 에 `ARG`/`ENV` 로 받고, `cloudbuild.yaml` 에서 `--build-arg` 로 넘깁니다.
> 값이 비어 있으면 화면은 떠도 **API 호출만 실패**합니다 (화면만 뜰 때가 제일 속삭입니다).

## 6. 로컬 개발 3단계

```bash
# ① 환경변수 준비
cp .env.example .env.local

# ② 개발 서버
pnpm dev        # http://localhost:3000
```

| 자주 쓰는 명령 | 하는 일                                  |
| -------------- | ---------------------------------------- |
| `pnpm dev`     | 개발 서버                                |
| `pnpm build`   | 프로덕션 빌드                            |
| `pnpm test`    | 테스트                                   |
| `pnpm lint`    | 린트                                     |
| `pnpm format`  | 자동 포맷 (CI 가 `format:check` 로 확인) |

> 백엔드가 아직 없으면 `next.config.mjs` 의 rewrite 기본값(`localhost:5010`)을 씁니다.
> 백엔드를 같이 띄우려면 백엔드 repo 의 [`docs/배포-런북.md`](../15th-docthru-team2-be/docs/배포-런북.md) 의 로컬 개발 절차를 보세요.

## 8. 자주 나는 문제

| 증상                                       | 원인                                            | 해결                                                      |
| ------------------------------------------ | ----------------------------------------------- | --------------------------------------------------------- |
| 화면은 뜨는데 API 가 500                   | `BACKEND_BASE_URL` 이 빌드 시점에 안 박힘       | `cloudbuild.yaml` 의 `_BACKEND_BASE_URL` 확인 → main 머지 |
| 공유 미리보기가 `localhost` 로 나감        | `NEXT_PUBLIC_SITE_URL` 미주입                   | 同上                                                      |
| CI 가 `format:check` 에서 실패             | 포맷이 밀림                                     | `pnpm format` 후 커밋                                     |
| CI 가 `Build` 에서 실패                    | 타입·린트 오류                                  | 로컬에서 `pnpm build` 로 재현                             |
| Cloud Build 가 `requires BuildKit` 로 실패 | Dockerfile 에 BuildKit 전용 문법                | `RUN --mount=type=cache` 사용 금지                        |
| Cloud Build 가 `Corepack … HTTP 503`       | corepack 이 npm 레지스트리 메타데이터를 못 받음 | Dockerfile 이 tarball 직접 설치 방식 (적용 완료)          |

## 9. 브랜치 보호 규칙 설정 (repo 소유자가 해야 합니다)

> ⚠️ **현재는 보호 규칙이 없어서 아무나 `main` 에 바로 push 할 수 있습니다.**
> 아래를 repo 소유자(`emmet-lv99`) 계정으로 한 번만 설정해 주세요.

**콘솔로**

1. `Settings` → `Branches` → `Add rule`
2. **Branch name pattern** → `main`
3. ✅ `Require a pull request before merging`
4. ✅ `Require status checks to pass before merging` → **`verify` 추가**
5. ✅ `Do not allow bypassing the above settings`
6. 같은 방법으로 `develop` 도 추가 (리뷰 개수는 0 으로 두면 됩니다)

**터미널로 (admin 권한이 있는 계정에서)**

```bash
gh api -X PUT repos/emmet-lv99/15th-docthru-team2-fe/branches/main/protection \
  --input '{"required_status_checks":{"strict":true,"contexts":["verify"]},"enforce_admins":true,"required_pull_request_reviews":{"required_approving_review_count":1,"dismiss_stale_reviews":true},"required_conversation_resolution":true,"allow_force_pushes":false,"allow_deletions":false}'
```

> 상태 체크 이름은 워크플로 job 이름인 **`verify`** 입니다 (GitHub Actions 의 `CI` 워크플로가 만드는 체크).
